# Comments adapter evidence

Inspected 2026-09-12. Protocol reference: [ultrazg/xyz comment handler](https://github.com/ultrazg/xyz/blob/22cfe7848a98b393a5f9f62c5e9a4eea2592eb1b/handlers/comment.go), commit `22cfe7848a98b393a5f9f62c5e9a4eea2592eb1b`, commit date 2026-08-13. Parameter and response descriptions: [primary comments](https://github.com/ultrazg/xyz/blob/22cfe7848a98b393a5f9f62c5e9a4eea2592eb1b/doc/docs/commentPrimary.md), [threads](https://github.com/ultrazg/xyz/blob/22cfe7848a98b393a5f9f62c5e9a4eea2592eb1b/doc/docs/commentThread.md). This is an unofficial protocol reference, not a platform stability guarantee. Starling's adapter is independently implemented; third-party implementation code is not incorporated.

## Read contract

The optional `provider.CommentReader` leaves the existing Provider interface compatible. Reads require the current account access token. Requests reuse Client.request, its rate limit handling and read retry policy, the existing random per-lifetime device UUID and honest Starling User-Agent. No mobile identity or official app headers are copied.

| Operation | Request | Pagination |
| --- | --- | --- |
| Primary comments | POST `/v1/comment/list-primary`, `owner: {id: episodeID, type: EPISODE}`, `order: HOT` or `TIME` | Opaque local cursor binds episode ID, normalized order and the response `loadMoreKey` object. Both require stable `id`, `direction: NEXT`, optional string `section`; HOT requires numeric `hotSortScore`, TIME does not. No guessed page limit. |
| Expand thread | POST `/v1/comment/list-thread`, `primaryCommentId`, `order: SMART` | Source supports no request cursor. Nonempty thread cursor is rejected with UNSUPPORTED before sending. A continuation response remains partial without an actionable cursor. |

`TIME_ASC` is not documented; the thread reference specifies SMART or TIME. Episode ID is checked locally and response owners must match the requested episode. Text is normalized as plain text, with id, author identity, createdAt and threadReplyCount. Inline `replies` on primary items are previews and are not treated as complete threads. Missing/invalid stable IDs, owner mismatch, invalid dates, malformed author/text/counts and within-page duplicate IDs reject the page. Avatar URLs use the existing image allowlist.

The direct upstream envelope contains `data: []`; the extra outer `data` shown in xyz documentation belongs to its proxy wrapper. Primary absence of loadMoreKey means terminal according to the source and live observation. A lone nonempty loadNextKey is rejected instead of silently treated as terminal. Threads require explicit pagination evidence or a nonnegative totalCount equal to the number of returned items to claim completeness. Missing evidence or fewer rows than totalCount stays partial; it never means all replies loaded. Unsupported pagination requires the official client for remaining replies.

## Verification boundary

Unit fixtures in comments_test.go are deliberately synthetic. They exercise body/header construction, primary cursor roundtrip, normalization, missing authentication, invalid IDs/cursors, terminal/partial responses and unsupported thread continuation. They do not prove current platform availability.

The opt-in `TestLiveCommentsReadOnly` uses only Starling's own session.vault, never refreshes or saves credentials, and sends no mutation requests. It logs envelope/cursor field names, order, status and counts only, not account identifiers, comment text, tokens or cursor values. Set `STARLING_LIVE_COMMENTS=1`; optionally choose `STARLING_LIVE_COMMENT_EPISODE`. Otherwise the first item on the first favorites page is used. The probe reads at most two primary pages per order (HOT and TIME), plus at most two existing threads selected from HOT roots with positive replyCount. It also checks sampled TIME dates descend across the page boundary. Thread logs include expected/returned counts, completeness and the number of rows with normalized primary/reply-reference relationships. This bounded sample does not prove large-thread pagination, all accounts, all episodes or future availability.

Live result on 2026-09-12: success with the existing honest Starling headers. Primary page 1 returned 15 items with `data, loadMoreKey, loadNextKey, totalCount`; page 2 returned one item with `data, loadPrevKey, totalCount`, confirming a nonempty terminal page without loadMoreKey. Two sampled threads each had one expected reply and one returned reply, with `data, totalCount` and no cursor. No credential refresh/save and no comment create/delete/like request was performed.

Sorting follow-up on 2026-09-12: both HOT and TIME returned 15 items on page 1 and one terminal item on page 2, with successful continuation. HOT's continuation fields were `direction, hotSortScore, id, section`; TIME's were `direction, id, section` (no hotSortScore). All 16 sampled TIME items had descending createdAt values across both pages. The documented TIME order and its score-free cursor were thus live verified on this one episode, with no write or credential refresh/save operation.

`model.CommentOrder` accepts `hot` and `latest`; empty means hot, other values produce INVALID_ORDER. The optional `SortedCommentReader.CommentsOrdered` maps these to HOT/TIME. Existing `CommentReader` and `Client.Comments` remain available, with Comments delegating to hot. New cursors bind the episode ID and normalized order; cross-episode, cross-order and legacy unbound cursors fail BAD_CURSOR before a request. The encoded cursor retains the existing 8192-byte input cap, and raw upstream cursor objects have a local 5000-byte cap so the wrapped representation stays within that limit. These are local safety limits, not upstream pagination semantics. Synthetic sorting tests cover TIME key roundtrip, order mapping, scope mismatch without requests, malformed score/order and cursor size. Reply creation is outside this sorting phase.

## Top-level plain-text creation

The optional `provider.CommentWriter` sends exactly one POST `/v1/comment/create` with `{text, owner: {id: episodeID, type: EPISODE}}`. It omits replyToCommentId and reuses the existing honest Starling headers. Its request uses `retryRead=false`: no automatic HTTP retry, credential refresh, or replay. Source: the pinned handler above and [create documentation](https://github.com/ultrazg/xyz/blob/22cfe7848a98b393a5f9f62c5e9a4eea2592eb1b/doc/docs/commentCreate.md).

The direct success body has `data: {id, author, owner, text, createdAt, replyCount, ...}` and optional toast. Starling requires the same stable identity/owner/text/date checks as comment reads, maps create's replyCount into the normalized reply count, and discards the extra personal fields in the upstream author object. It does not assume the returned text must exactly echo the request. A valid server response is necessary to report confirmed success; a toast alone is insufficient.

Source provides no known platform character limit or comment-specific business error catalog. `model.ValidateCommentText` rejects invalid UTF-8, all-Unicode-whitespace text, NUL characters and more than 1 MiB of text as a local transport safety limit. This is not a claim about upstream text length allowances. Nonempty text, including leading/trailing whitespace and line breaks, is transmitted unchanged as plain text.

Explicit authentication, forbidden, rate limit and business rejection responses preserve their safe existing error codes. Network/cancellation/upstream failures, redirects or malformed success responses return COMMENT_UNCERTAIN: the user must refresh comments or check the official client before deciding whether to send again. No response body or draft text is included in error messages. Even failures that occur before dispatch inside the shared transport are conservatively uncertain when dispatch timing cannot be established.

Synthetic creation tests verify the precise request, normalized result, Unicode validation, one request on HTTP 401/403/429/503/business rejection, malformed-success/redirect/network/cancellation handling and error privacy. Real comment creation is **not live verified**: no mutation has been sent during development. The request contract supports explicit user-driven creation; real account acceptance remains to be checked by the user through that flow.

## Replies and relationship confirmation

The optional `CommentReplyWriter.ReplyComment` takes both the direct reply target ID and the locally verified primary comment ID. It uses the same single-attempt write transport as top-level creation. The upstream body adds only `replyToCommentId`; local `primaryCommentID` is never sent as an invented upstream parameter. The pinned handler and create documentation explicitly describe replyToCommentId as the switch between a top-level comment and a reply. Direct replies use the primary comment as target; nested replies use the selected reply as target and retain the primary root locally.

The normalized Comment now includes optional `primaryCommentId` (upstream `thread`) and `replyTo: {id, nickname, summary}` (upstream `replyToComment`). Summary contains at most 200 Unicode code points of the referenced plain text. Reference owner and ID must be valid and belong to the requested episode; any supplied target thread must agree with the enclosing thread. A thread read also rejects a supplied thread ID different from the requested primary comment. Missing thread/reference metadata does not fabricate a relationship: the row can remain readable, but missing primary metadata cannot authorize a nested reply target. A reference without owner is not promoted into normalized replyTo.

Successful reply creation requires the returned thread to equal the selected primary comment and the returned direct target to equal the selected reply target. Missing or conflicting relationships produce COMMENT_UNCERTAIN, even on HTTP 200. A top-level creation response that includes a nonempty thread or nonnull reply object is rejected as an unconfirmed result instead of being mislabeled as a root comment. All error messages stay free of draft or server-response text.

Reply mutation tests use synthetic data only: they cover direct/nested request mapping, Unicode summary truncation, reference/episode/primary validation, missing metadata on reads, wrong or missing relationships on write responses, HTTP 401/403/429 without replay and a timeout after dispatch returning COMMENT_UNCERTAIN. No live replies or root comments were sent. Real account acceptance of reply creation remains unverified.

Final read-only relationship check on 2026-09-12: the explicit probe ran once with the new decoder. Both sampled existing threads returned one item for one expected reply, complete=true; each had one normalized primary relationship and one reply reference. Their envelopes contained data and totalCount. HOT and TIME again returned 15 plus one terminal item; TIME date ordering passed. This confirms the new relationship decoder can read those two existing threads, not acceptance of a new reply. No account/content identifiers were logged and no credentials were refreshed or saved.

## Application and UI contracts

The existing JSON Call bridge adds `comments.list {epoch,episodeId,cursor,order?: "hot" | "latest"}`, `comments.thread {epoch,episodeId,commentId,cursor}` and `comments.create {epoch,episodeId,text,requestId,replyToCommentId?,primaryCommentId?}`. Reads return CommentPage; creation returns `{comment: Comment}` only after provider validation and author/account matching. No Wails binding signature or database migration is required.

Service uses epoch-bound reads and `session.DoOnceAt` for writes. A current epoch admits one active create request and retains admitted request IDs until epoch change/logout; repeated IDs are rejected even after failure. The in-memory ledger retains no text or full responses, rejects new IDs after 4,096 attempts instead of evicting protection, and is not upstream idempotency or cross-process protection. Authentication failure never triggers a write replay. An older token's 401 does not invalidate a concurrently refreshed token.

The service retains only ID relationships from successful reads, bound to epoch and episode. Replies require both a known primary root and a direct target mapped to that root; missing, cross-episode or stale associations produce COMMENT_TARGET_INVALID before dispatch. Both optional reply IDs must be supplied together; empty values retain root publication.

UI retains lists separately by account/epoch, episode and order, with independent cursors, errors and reading positions. Draft, error and uncertain state are separated by reply target, shared across sorting tabs. Root publications have separate confirmation feedback; replies are confirmed only in their originating flat thread and refresh that thread. Cached platform IDs remove duplicate confirmation feedback. A successful background publication updates only its originating episode; logout/account replacement discards late outcomes. Refresh and acknowledgment do not send comments. For uncertain outcomes, the ordinary send action stays disabled: the user can explicitly acknowledge having found the comment and clear the draft, or confirm it is absent and submit a new request ID. Closing the application or clearing local state cannot undo a platform mutation.
